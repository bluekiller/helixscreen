# Installer UX: steps, plan screen, dry-run

Status: design approved in conversation 2026-10-06, awaiting spec review.

## Goal

The installer (`scripts/lib/installer/*.sh`, bundled into `install.sh` by
`scripts/bundle-installer.sh`) works, but its output reads like a debug log: about 1000
`log_*` calls print as they happen, raw apt and systemctl output leaks through unprefixed,
and the sudo password prompt lands in the middle of apt's output. A regular user should
see a short, confident run: what was found, what will change, each step as it completes,
and a summary. Everything else stays available, in a log file always and on screen with
`--verbose`.

It stays a CLI, stays POSIX sh that runs under BusyBox ash, and adds no dependencies.

### Where it runs

The same output has to read well in all four places the installer runs:

| Caller | stdin | stderr | Notes |
|--------|-------|--------|-------|
| `curl ... \| sh` over ssh | the script | terminal | prompts must read `/dev/tty` |
| KIAUH extension (`helixscreen_extension.py#_run_installer`) | the script | terminal | passes `--update` / `--uninstall`; asks its own confirm first |
| in-app updater (`update_checker.cpp`, `HELIX_SELF_UPDATE=1`) | none | file `/var/log/helixscreen-install.log` | `--local <tarball> --update`; NoNewPrivileges, so no sudo |

Moonraker's update_manager does NOT run install.sh: it unpacks the release zip itself and
`helixscreen-update.path` restarts the service via `config/refresh-service-units.sh`. That
script's own output (`qidi-3mf-thumbs-units.sh`) is the only installer-adjacent output a
Mainsail update produces; it is quieted in Task 5.

## 1. Output

### Terminal run

```
<braille logo>   HelixScreen
                 v1.1.0-beta.4 · beta channel

  ✓ Checked system          Raspberry Pi 4 · Kalico · systemd
  ✓ Installed libraries     libgles2
  ✓ Downloaded              100 MB · SHA256 verified
  ✓ Stopped KlipperScreen
  ✓ Installed files         ~/helixscreen
  ✓ Set up service
  ✓ Connected to Moonraker  update manager · config editable in Mainsail
  ⠹ Starting HelixScreen…
```

- A step shows a spinner while running, then resolves to `✓ <title>  <detail>` or `✗ <title>`.
- Steps with nothing to do are not shown (no missing libraries, no "Installed libraries" line).
- `log_warn` / `log_error` always print, indented under the current step.
- Non-UTF-8 locale: `✓`/`✗`/spinner fall back to ASCII (`ok`, `FAIL`, `|/-\`), and the braille
  logo is dropped in favour of the logotype alone.

### No terminal

Each step prints once, when it finishes, with no color, cursor movement or spinner:

```
HelixScreen installer v1.1.0-beta.4 (beta)
[1/8] Checked system ... ok (Raspberry Pi 4, Kalico, systemd)
[3/8] Downloaded ... ok (100 MB, SHA256 verified)
```

Step numbers are fixed per run once the plan (section 2) is known, so skipped steps are
left out of the count rather than shown as gaps.

### Summary

The run ends with a short block that replaces the hints now scattered through the output
("You can now edit HelixScreen config from Mainsail/Fluidd", "Restart KIAUH ...", "You can now
update HelixScreen from the Mainsail/Fluidd web interface!"):

```
HelixScreen v1.1.0-beta.4 is running (beta channel).

  Config     ~/printer_data/config/helixscreen  (editable in Mainsail)
  Updates    Mainsail → Machine → Update Manager, or re-run with --update
  Disabled   KlipperScreen  (re-enabled by --uninstall)
  KIAUH      restart KIAUH to see the HelixScreen extension
  Log        ~/printer_data/logs/helixscreen-install.log
```

### `--verbose`

Prints every `log_info` line live in today's `[INFO]` form under the step headers, plus
`run_logged` command output. The step headers and the summary still print.

### Logo

Pre-rendered braille art of `assets/images/helix-icon-256.png`, cropped to the ribbon's
bounding box, 26x10 cells, generated by chafa:

```
chafa --format symbols --size 26x10 --symbols braille --colors 256 --polite on ribbon.png
```

Shipped as two static files (256-color and 16-color) inside the installer, so chafa is a
build-time tool only. A `scripts/render-installer-logo.sh` regenerates both. The
logotype is text: "Helix" in blue (256-color 33), "Screen" as a red to orange ramp
(197, 203, 209, 214). 16-color and no-color terminals get the nearest ANSI colors or plain
text. No terminal: one plain line.

### Mechanism (all in `common.sh`)

| Function | Behaviour |
|----------|-----------|
| `step "<title>"` | Opens a step: spinner on a terminal, nothing yet without one. Writes a marker to the log. |
| `step_done ["<detail>"]` | Resolves the open step to ✓ with optional detail. |
| `step_fail` | Resolves it to ✗ and prints the failure block (section 3). |
| `step_skip` | Closes a step that turned out to have nothing to do, without printing it. |
| `log_info` | Log file always; screen only with `--verbose`. **This is the behaviour change that quiets ~1000 call sites without editing them.** |
| `log_note` | New: a detail line regular users should see on screen. Used sparingly; candidates are promoted one by one from today's `log_info`. |
| `log_warn` / `log_error` / `log_success` | Unchanged prefixes, indented under the open step. `log_success` inside a step goes to the log like `log_info`. |
| `run_logged <cmd...>` | Runs a command with stdout+stderr appended to the log; silent on success; on failure prints the command, exit code and the last 15 lines. Uses a temp file, not a pipe, so the command's exit code survives under ash. `--verbose` also echoes output live. |

The spinner runs in the foreground between calls, not as a background process: a step
redraws its spinner frame whenever it logs, and `run_logged` polls its child to animate
while the command runs. No background spinner process means nothing to kill or orphan.

Uncolored lines today get fixed at their source by routing through `run_logged`:
`apt-get install` (`requirements.sh`), systemctl's "Created symlink" (`service.sh`),
`config/qidi-3mf-thumbs-units.sh` (its `qlog` lines), the polkit restart.

## 2. Plan screen and `--dry-run`

### One check pass

`main()` is split at a **confirm point**. Everything before it only reads; everything after
it changes the machine. The read-only pass covers what `main()` already detects (platform,
firmware, Klipper user, init system, existing install, channel and version, disk space,
manifest availability) plus three detections pulled out of functions that currently act as
they detect:

| Today | Split into |
|-------|-----------|
| `install_runtime_deps` runs `apt-get install` immediately | `detect_missing_runtime_deps` (before the confirm point) + `install_runtime_deps` (after) |
| `stop_competing_uis` finds and stops in one go | `detect_competing_uis` + `stop_competing_uis` |
| Moonraker / KIAUH integration decided while writing | `detect_moonraker_integration` reports what exists vs. what would be added |

Pre-confirm code that writes or may prompt for sudo today, and what happens to it:

| Today | Change |
|-------|--------|
| `check_requirements` apt-installs `unzip` | detect only; install after confirm |
| `install_runtime_deps` apt-installs libraries | split (table above) |
| `set_install_paths` → `cleanup_ad5m_gcodes_root` deletes old archives (AD5M) | moved after confirm |
| `mod_payload_mode_block` → `record_payload_root` mkdir + tee (payload hosts) | moved after confirm |
| `detect_tmp_dir` probes writability with `$SUDO test -w` | plain `test -w` before confirm; sudo probe after |
| `check_disk_space` `dd` probe with `$SUDO` | `sudo -n` only before confirm; undetermined reads as "would check after sudo" |

### Plan screen

```
<logo>

  Printer    Raspberry Pi 4 · Kalico · systemd · user pbrown
  Found      HelixScreen (no config) at ~/helixscreen
  Install    v1.1.0-beta.4 (beta) · 100 MB · SHA256 available
  Libraries  libgles2 (apt)
  Disable    KlipperScreen
  Add        Moonraker update manager · service allowlist · KIAUH extension
  sudo       needed for: service, libraries, udev and polkit rules

Continue? [Y/n]
```

| Run | Behaviour |
|-----|-----------|
| fresh install, terminal | Shows the plan and asks. The answer is read from `/dev/tty`, never stdin (stdin is the script under `curl \| sh`). Nothing in the installer reads `/dev/tty` today (the three existing prompts read stdin behind `[ -t 0 ]`); `tty_confirm` in `common.sh` is new and the `--clean` prompt moves onto it. |
| `--yes`, or no terminal | Shows the plan, continues without asking. |
| `--update` | Shows a short plan (`Update v1.1.0-beta.3 → v1.1.0-beta.4`), never asks: `--update` is the decision. |
| `n` / EOF | Exits 0, "Nothing changed." |

After confirmation, one `sudo -v` with a one-line reason, so the password prompt never
interrupts a later step. Skipped when root or when no step needs sudo.

### `--dry-run`

Runs the check pass for real, including network reads to confirm the release and its
manifest exist (no download), prints the plan screen with "Dry run, nothing changed.", and
exits.

- Exit 0 when the install would proceed; non-zero (the failing check's existing exit code) when a check would stop
  it: insufficient disk, wrong architecture, no release for this platform, unsupported
  firmware.
- Never invokes sudo. A check that needs root reports "would check after sudo".
- Works with `--update`, `--version`, `--local`.

### Enforcement

There is no `DRY_RUN` guard sprinkled through the code. Dry-run exits at the confirm point,
and the invariant "nothing before the confirm point mutates" is enforced by:

1. the e2e dry-run test (section 4), which proves it on the Debian sandbox host, and
2. a static check in `scripts/check_installer_step_reachability.py`: every function `main()`
   calls before the confirm point must be on an allowlist of read-only functions. This
   catches a mutation added on a K1/AD5M/mod-payload branch the sandbox never runs.

## 3. Logging and failures

### Log file

- Every line: all `log_*` output, `run_logged` command output, step markers, timestamps
  (`[HH:MM:SS]`, per the project's logging rule).
- Written to the installer temp dir during the run, moved at the end to
  `printer_data/logs/helixscreen-install.log`, where Mainsail's log viewer shows it.
  Hosts without printer_data (bare `/opt`, AD5M, K1): `<install>/logs/helixscreen-install.log`.
- The previous run is kept as `.1`, so a failed update does not overwrite the log of the
  install that worked.
- Never contains the sudo password (`sudo -v` reads the terminal directly).

### Failure block

```
  ✓ Downloaded             100 MB · SHA256 verified
  ✗ Installing libraries
      apt-get install libgles2 failed (exit 100):
        E: Could not get lock /var/lib/dpkg/lock-frontend. It is held by process 812 (apt)
        E: Unable to acquire the dpkg frontend lock
      Another apt process is running; wait for it to finish and re-run.

  Nothing on your printer was changed after this step.
  Full log: ~/printer_data/logs/helixscreen-install.log
```

- The command, its exit code, the last 15 lines of its output, then the step's hint (most
  existing `log_error` call sites already carry one).
- The closing state line comes from the existing rollback logic, not new guesses: before
  the atomic swap "Nothing on your printer was changed"; after it, what was rolled back or
  where the previous install was kept.
- `log_error` raised outside a `run_logged` command still prints, under the open step.

### Interruption

An EXIT/INT trap resolves the open step to ✗ "interrupted" and finalizes the log. The
existing rollback paths stay in charge of restoring state.

## 4. Testing

### Existing suite

`tests/shell/helpers.bash` stubs the `log_*` functions, and most installer tests then source the real `common.sh`, whose `log_info` would turn quiet. `helpers.bash` exports `HELIX_INSTALL_VERBOSE=1`, so `log_info` keeps printing in every existing test; only tests about default (quiet) output unset it.

### New unit tests (`tests/shell/test_installer_output.bats`)

- `step` / `step_done` / `step_fail` / `step_skip` in terminal and non-terminal modes
  (`HELIX_INSTALL_TTY=0|1` forces the mode; bats has no terminal).
- ASCII fallback under `LANG=C`; braille logo dropped there.
- `run_logged`: failing exit code survives under ash; tail printed on failure; full output
  in the log; silence on success.
- Log placement (printer_data vs `<install>/logs`) and `.1` rotation.
- INT during a step resolves it to ✗ "interrupted".

### e2e (`tests/shell/test_install_e2e.bats`, BusyBox ash sandbox)

- `--dry-run` mutates nothing: a checksum of the whole sandbox tree is equal before and
  after, and the systemctl/apt/sudo stubs record zero mutating calls.
- `--dry-run` exit codes: 0 for a good plan, non-zero for low disk and missing release.
- Confirm prompt through a pseudo-terminal (`script -qc`): `n` leaves the tree unchanged,
  `y` installs.
- `--yes` and no-terminal runs never prompt.
- Golden transcripts for no-terminal output (fresh install, update, failed apt), with
  timestamps normalized. These are exactly what Mainsail/KIAUH users see. Terminal-mode
  tests assert the final frame (✓ lines and summary) only; spinner frames are timing.

### Real devices (read-only before merge)

- `--dry-run` on the Voron V0 (192.168.1.133: Pi 4, systemd, Kalico).
- `--dry-run` on one BusyBox printer (K1C or AD5M), with permission asked first.
- After merge, a real `--update` on the V0.

## Out of scope

- Opting out of individual steps (keep KlipperScreen, skip KIAUH). Add when asked.
- Any change to what the installer installs or where.
- The uninstall flow's output. Same layer applies later; not designed here.
